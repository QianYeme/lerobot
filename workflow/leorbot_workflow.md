# LeRobot 视觉抓取项目：Codex 实验与工程工作流

> 适用范围：本仓库的数据处理、ACT/ACTDet/MASK/INJECT/关键点开发、训练、离线评估、远程 GPU 执行、真机部署和结果报告。
>
> 项目目标：让 SO-101 准确、流畅地完成装水透明杯的抓起—移动—放下，并能解释视觉辅助分支是否真正提高定位和闭环鲁棒性。
>
> 本文件是执行协议，不是插件。它用持久化合同、固定 Gate、证据文件和 Git 审计约束 Codex；脚本负责可自动检查的部分，用户负责高风险授权和最终目标取舍。

---

## 0. 为什么需要这套工作流

### 0.1 与直接使用 Codex 的区别

直接使用 Codex 通常是：

```text
用户提出任务 → Codex 依赖当前上下文修改/运行 → 在对话中汇报
```

它适合局部修复，但长周期机器人实验容易出现：

- 关键约束只在聊天中，换会话后丢失；
- 训练、离线评估和真机使用了不同的数据接口或控制参数；
- 看到结果后才改指标或挑 checkpoint；
- 失败日志被覆盖，无法解释结论如何形成；
- “代码跑通”“离线更准”“真机成功”被混为一谈；
- 本地、远程、Git 和机器人工作区版本漂移。

本工作流把它改成：

```text
实验合同 → 准备 Gate → Codex 内层执行循环 → 证据包
       → Builder Review → Red-Team Review → 用户决策 → 下一合同
```

区别不在 Codex 模型本身，而在于增加了持久、可检查的实验接口。

### 0.2 它是怎么实现的

1. **实验合同**：运行前固定问题、变量、数据、验收线和停止条件。
2. **状态机**：每轮只能处于 `DRAFT / READY / RUNNING / PASS / PARTIAL_PASS / FAIL / BLOCKED`。
3. **证据包**：结论必须回溯到命令、代码、配置、日志和原始指标。
4. **逐层 Gate**：从数据接口到真机闭环依次验收，前层失败不能靠后层漂亮结果掩盖。

能够自动化的 Gate 应写进脚本并产生 JSON 或完成标志；相机语义、透明杯标注和真机成功判定等人工环节必须记录证据。Markdown 只能规定流程，不能替代自动检查。

### 0.3 优点

- 可追溯、可回退，适合网络中断和跨会话接力；
- 固定状态维度、相机、预处理器和 episode 切分，减少口径漂移；
- 指标预注册，降低挑 checkpoint 和事后解释；
- 先用测试、真实批次 smoke 和短跑挡住错误，节省 GPU/真机时间；
- 合同范围内 Codex 可持续调试，不必让用户批准每个普通工程步骤。

### 0.4 缺点和控制办法

| 缺点 | 风险 | 控制办法 |
|---|---|---|
| Gate 和文档有成本 | 小改动也变慢 | 按风险分级，低风险走轻量路径 |
| 合同可能过时 | 机械执行错误前提 | 每次先核对日志、HEAD、数据和服务器状态 |
| 指标制造虚假确定性 | teacher-forced 被当成闭环成功 | 离线 Gate 与真机 Gate 分开 |
| 多角色造成搬运 | 用户反复复制材料 | Codex兼任实施和第一轮审查，高风险才独立复核 |
| 状态与真实进程不一致 | 文档写完成但任务已中断 | 退出码、产物审计和 done 标志共同证明 |
| 容易过度抽象 | 为一次实验建立空接口 | 只为真实变化点建立 seam |

## 1. 角色和授权

### 1.1 用户：项目负责人和真机安全负责人

用户负责目标、优先级和风险取舍；决定会改变数据语义、比较口径或真机协议的事项；提供遮挡可见性、相机物理语义和真机结果；明确授权高成本训练、外部发布、Git 提交/推送和真机动作。

### 1.2 Codex：主要研究工程师和第一轮审查者

Codex负责：

- 先读项目记忆、工作日志、Git 状态和证据；
- 把合同实现成最小必要代码并完成调试、测试、数据检查和监控；
- 保护用户未提交修改，不顺手改无关文件；
- 区分事实、测量、推断和未验证假设；
- 更新工作日志、报告，完成 Builder 和第一轮 Red-Team Review。

**Codex 可以自主改变“如何实现”，不能静默改变“比较什么、使用什么数据、怎样判定成功”。**

### 1.3 可选独立复核

以下情况建议增加只读独立审查：多路100k训练前；改变数据/schema/预处理；论文主结论冻结；真机控制修改；Builder 与 Red Team 冲突。独立审查使用同一证据包，不另起实验口径。

### 1.4 必须停止请求决策的情况

- 只有改变目标、数据语义或预注册验收线才能继续；
- 需要新权限、凭证、真机动作或破坏性操作；
- 多种解释会产生实质不同实验且现有证据无法选择；
- 真机存在碰撞、失控或洒水风险；
- 关键输入缺失且安全替代方案不可用。

普通代码或依赖错误不算语义 blocker，Codex应先在内层循环诊断。

## 2. 风险分级

- **L0 只读分析**：读日志、报告、checkpoint 配置；直接执行并指出来源。
- **L1 局部可逆修改**：脚本参数、测试、文档；写简短成功标准，跑针对性测试和 `git diff --check`。
- **L2 影响实验结果**：损失、模型、数据切分、标签、指标、预处理；必须有实验合同、回归测试和真实批次 smoke。
- **L3 高成本/外部状态**：多路训练、批量伪标签、上传、提交/推送；另需资源预算、恢复策略和明确授权。
- **L4 真机闭环**：另需部署一致性、安全检查、熔断、录像/CSV 和人工判定。代码通过测试不等于真机授权。

## 3. 双循环机制

### 3.1 内层工程循环

```text
复现 → 最小化 → 假设 → 插桩 → 修改 → 测试 → 真实批次 smoke → 收集证据
```

要求：每行改动对应合同目标；先证明失败再证明修复；不改无关代码；旧结果和失败现场默认保留；远程任务记录命令、screen/PID、日志、退出码和产物。

### 3.2 外层实验循环

```text
问题 → experiment.md(DRAFT) → 准备 Gate(READY)
→ 必要时用户授权 → 执行(RUNNING) → 证据包
→ Builder + Red-Team Review → PASS/PARTIAL_PASS/FAIL/BLOCKED
→ 更新工作日志/报告 → 用户决定下一步
```

同一问题的实现修复不必新开一轮；研究问题、主要变量或验收线改变时必须建立新合同。

## 4. 每轮实验合同：experiment.md

L2–L4运行前必须写清以下内容。可放在对应 `outputs/<campaign>/<run_id>/`，不重复已有报告。

### 4.1 问题与假设

- 本轮只回答什么；为什么现有证据不足；
- 预期机制；什么结果会反驳假设。

### 4.2 单变量与对照

- 基线与候选；唯一主要变量；
- 固定 seed、步数、统计量、切分、相机和控制参数；
- 共有权重是否真正对齐。相同 seed 不自动等于相同初始化。

### 4.3 数据合同

- 数据集路径、版本/hash、episode 和帧数；
- train/dev/val/test 明细；
- state/action 名称、顺序；相机键、物理含义、尺寸和fps；
- 标签来源及遮挡、未知、缺标如何进入损失；
- 是否含部署不存在的泄漏字段，例如 `master_gripper.pos`。

固定 val10 只用于正式比较；若频繁用于调参，必须降级为开发集。

### 4.4 模型与训练合同

- checkpoint 起点、结构开关、新参数；预/后处理器；
- loss 与权重；batch、steps、学习率、AMP、保存频率；
- 增强与标签一致性；GPU、时长、磁盘预算；中断恢复规则。

### 4.5 评估与部署合同

- teacher-forced 与闭环指标分别是什么；
- h0、动作块冲突、阶段误差和事件延迟定义；
- `n_action_steps`、temporal ensemble、`max_relative_target`；
- 起始位、杯位、水位、光照、相机编号；
- 成功、失败、洒水、掉杯和熔断定义。

### 4.6 预注册 PASS 条件

固定必过 Gate、主指标、改善阈值、护栏指标、样本/试次数、证据不足条件和明确不回答的问题。看到结果后不得改门槛迎合候选；门槛设计错误时结束本轮并新建合同。

## 5. 八层验收 Gate

前层失败时，后层结果只能用于诊断。

### Gate 1 — Provenance：究竟运行了什么

核对本地/远程/HEAD、dirty worktree归属、命令/config/环境/seed/时间/退出码、checkpoint完整性和覆盖风险。

### Gate 2 — Data & Interface：数据与部署接口

核对state/action维度名称顺序、主臂字段、切分互斥、episode/frame与视频映射、top/gripper语义与尺寸、stats和processor来源、标签与增强对齐。

### Gate 3 — Implementation：实现是否符合合同

核对单元/回归测试、decoder/FPN/backbone/action梯度、遮挡/忽略梯度、默认关闭兼容性、坏标签明确失败、推理不依赖训练标签。

### Gate 4 — Training Health：训练是否健康

核对done/退出码/最终step/checkpoint、NaN/Inf/OOM、loss量级和grad norm、gate/α状态、同预算同数据；短训只用于排错，不默认代表100k排名。

### Gate 5 — Offline Evaluation：离线证据是否回答问题

固定episode/checkpoint；拆分arm、gripper、阶段、事件、冲突；报告逐episode配对；排除“少动所以平滑”；记录异常值；明确teacher-forced不能证明闭环。

### Gate 6 — Deployment Equivalence：部署一致性

核对真机state与config/meta、人工相机确认、processor、任务文本、频率、动作后处理、ensemble/限幅，并记录target、sent和actual。

### Gate 7 — Real-Robot Task：是否完成任务

检查抓取、移动、放下、整体成功；定位偏差、悬停、抽搐、过冲、提前闭爪、洒水、掉杯；保留失败录像/CSV；核对试次数和熔断。

### Gate 8 — Conclusion：结论有没有超过证据

检查单seed外推、固定杯位外推、单episode驱动、工程跑通冒充方法有效、反例和限制、报告/日志/论文是否来自同一冻结结果。

每个 Gate 为 `PASS / FAIL / NA`。整轮为：

- `PASS`：预注册目标和所有必需 Gate 通过；
- `PARTIAL_PASS`：有效推进但不能进入依赖该结论的生产阶段；
- `FAIL`：关键实现、数据、实验或假设被否定；
- `BLOCKED`：需要用户决策或新权限。

## 6. Builder 与 Red-Team Review

### Builder Review

回答是否按合同完成、哪些检查实际运行、是否达到门槛、产物如何复现、哪些没有完成。

### Red-Team Review

主动攻击：

- 主臂/未来信息泄漏；相机接反；train/val重叠；
- 未知被当背景、遮挡中心被插值、SAM漂移冒充真值；
- loss降低但动作分支无有效梯度；
- 改善来自少动、单集、挑checkpoint或短预算误判；
- teacher-forced被外推到闭环；
- ensemble、限幅或初始姿态造成不公平；
- 失败运行被覆盖或只报告成功样本。

两轮都支持才标为 `CONFIRMED`，否则为 `PROVISIONAL / REJECTED / BLOCKED`。

## 7. 退化测试和不变量

新因素关闭后必须尽可能回到基线：

- I1 `alpha=0`、共有权重相同时，动作输出精确回退 DET；
- `use_water_keypoint=false` 时旧checkpoint参数键和推理不变；
- 辅助标签全遮挡时辅助梯度为零、动作梯度仍存在；
- 推理移除标签文件后动作输出不变；
- 去主臂数据除state字段外，动作、图像、时间和episode保持不变；
- batch size不改变确定性指标定义；
- 训练评估和真机的state名称、顺序和尺度一致。

无法设计退化测试时，合同必须解释并增加更强对照。

## 8. 证据和目录

### 8.1 控制文档

- 当前进度：`docc/日志/工作日志.md`；
- 长期方案：`docc/方案与规划/`；
- 阶段结论：`docc/报告/`；
- 运行方法：`docc/指南/`；
- 实验合同和证据：对应的 `outputs/<campaign>/` 或训练记录目录。

### 8.2 推荐实验目录

```text
outputs/<campaign>/<run_id>/
  experiment.md
  command.sh
  manifest.json
  logs/
  metrics.json
  validation.json
  summary.md
  run.done              # 仅审计成功后写入
  raw/                  # 大数组/逐帧预测/图，通常gitignore
```

不为形式迁移历史产物。manifest至少记录run_id、目标/状态、commit/diff、数据/split、checkpoint、命令/config、环境/GPU、seed、时间、退出码、产物/hash和限制。validation记录Gate 1–8、schema、切分、训练健康、指标、部署参数、真机试次和最终状态。

### 8.3 失败证据

保留首个可解释失败日志；重跑用新run_id或明确备份；`run.done`只能在退出码和产物审计通过后创建；summary区分“失败后修复”和“从未运行”。

## 9. Git、本地、远程和发布

### 9.1 工作区保护

- 开始前 `git status --short`；用户已有修改不可覆盖或顺手格式化；
- 禁止用 `git reset --hard`、`git checkout --` 清理用户文件；
- 同步前比较HEAD、状态和关键文件hash；大型gitignore产物仍需manifest。

### 9.2 提交规则

原数学流程的 `git add .` 不适合共享脏工作区。改为：

```text
列出本轮文件 → git diff/diff --check → 验证
→ 用户要求提交时仅显式stage本轮文件 → commit
→ 用户要求推送时再核对远端并push
```

Codex不因一轮完成而自动提交或推送，commit也不能替代证据包。

### 9.3 远程和发布

- 凭证不写入项目；长任务用screen/tmux；启动前检查GPU、磁盘、数据、配置和输出；
- 并行前计算显存/磁盘；断线后先查进程/done/日志，不盲目重启；
- 关键小结果同步本地，重要模型按授权发布；
- GitHub/Hugging Face发布前检查凭证/隐私，模型包含config、权重、pre/postprocessor，并记录数据、schema、commit和限制。

## 10. 真机安全和公平比较

### 开测前

检查GPU、串口、相机、急停和工作区；人工查看暖机后的top/gripper画面；从checkpoint与meta双重核对state；干跑加载；固定控制参数、杯位、水位、光照、起始姿态和顺序。

### 开测中

每段保留录像和CSV；明显失控、碰撞、连续三次不追杯或洒水风险时熔断；失败也记录；不临时给失败模型更有利参数。

### 结论层级

- 1–2次：管道smoke；
- 每模型约10次：pilot，只看方向和失败模式；
- 每核心模型20–30次且杯位配对：项目主对比；
- 新光照/杯位/遮挡：单独鲁棒性实验，不与固定条件混算。

## 11. 当前项目阶段地图

```text
P0 目标与历史审计
P1 数据/schema/泄漏与部署一致性
P2 模型实现、退化测试、真实批次smoke
P3 小规模训练与开发集诊断
P4 同预算正式训练
P5 固定验证集离线评估和checkpoint趋势
P6 真机pilot和失败模式分析
P7 扩试、鲁棒性和消融
P8 结果冻结、论文和模型发布
```

当前阶段、冻结结论、下一步和阻塞项统一维护在`workflow/STATUS.md`。本文件不再保存动态项目状态，避免稳定流程因实验推进而过期。

## 12. 用户交互和汇报

每次阶段汇报优先回答：结果是什么；哪些是事实/推断；运行/未运行哪些测试；证据在哪；最大风险；下一步及成本；是否需要用户选择或授权。

用户说“继续”“下一步”或等价明确指令，可以授权已讨论清楚、风险未扩大的下一工程步骤；不自动授权真机、外部发布、破坏性操作或新的高成本训练。实质改变实验问题前，Codex先给出新合同摘要。

## 13. 总原则

1. 代码能运行不等于模型有效；离线有效不等于真机成功。
2. 训练、评估、部署必须共享数据接口和预处理语义。
3. 一轮尽量只改变一个主要因素并保留对照。
4. 新模块优先提供关闭开关和退化测试。
5. 未知不是背景，遮挡不是负样本，插值不是人工真值。
6. 短训用于排错和观察机制，不默认决定100k排名。
7. 验收线预先确定，失败证据和反例必须保留。
8. 保护用户工作区；提交、推送和发布需要明确范围。
9. 真机安全优先，参数公平优先于现场追求成功。
10. 最终结论必须追溯到合同、代码、数据、命令、日志和原始指标。
