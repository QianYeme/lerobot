## 第一阶段：先验收，不设计下一轮

先对照本轮 `decision.md`：

- Research Question
- Baseline / Intervention
- Frozen Contract
- Hypothesis
- Falsification Conditions
- Mandatory Gates
- Primary Metric
- PASS / FAIL / STOP
- Authorization

判断 Codex 是否真正完成本轮目标。

检查：

- 数据是否有效；
- baseline 是否公平；
- 是否有实现偏离；
- 是否有 schema / deployment mismatch；
- 是否存在遗漏、异常、旧结果误用；
- 是否发生未经授权的研究语义变化；
- 是否发生 Test contamination；
- 是否发生 checkpoint / seed cherry-picking；
- 是否存在“模块加入了但其实没被使用”的问题。

## 第二阶段：按 Gate 顺序验收

按当前 decision 要求检查：

```text
G0 Provenance / Contract
G1 Data & Schema
G2 Implementation & Regression
G3 Training Health
G4 Mechanism
G5 Offline Behavior
G6 Deployment Equivalence
G7 Real Robot
G8 Scientific Conclusion
```

不适用的 Gate 可以是 `NA`，但不能把 `NA` 当作 PASS。

不能因为：

- 代码能运行；
- loss 下降；
- 曲线好看；
- detector 能检测；
- 某次真机成功；

就跳过前面 Gate。

## 第三阶段：Red-Team Review

把自己当作反方，主动尝试证明当前结论是错的。

重点检查：

- data leakage；
- shortcut；
- confounder；
- seed luck；
- unfair baseline；
- post-hoc threshold；
- checkpoint cherry-picking；
- Final Test 泄漏；
- deployment mismatch；
- 模块存在但未被策略使用；
- 任务成功其实由 heuristic/controller 单独贡献；
- 不合理删除失败 episode；
- 把局部鲁棒性夸大成大范围泛化；
- 把 engineering PASS 误写成 scientific PASS。

如果 Codex 提供了 `proposal.md`，只能把它作为下一步候选建议，不能把 proposal 当成本轮已经验证的结论。

## 第四阶段：给出正式验收状态

本轮总体状态只从以下选择：

```text
PASS
PARTIAL_PASS
FAIL
BLOCKED
INVALID
```

并明确：

- 哪些结论是 `OBSERVED`
- 哪些是 `SUPPORTED`
- 哪些是 `OFFLINE_CONFIRMED`
- 哪些是 `REAL_ROBOT_CONFIRMED`
- 哪些应 `REJECTED`
- 哪些仍 `BLOCKED`

claim 强度不得超过 evidence。

## 第五阶段：用简单通俗中文向我汇报

重点回答：

1. 这一轮到底做了什么？
2. 最重要的结果是什么？

4. 假设有没有被支持，还是被反驳？
5. 如果方法有效，效果体现在哪里？
6. 如果失败，失败的是工程、机制、行为还是真机？
7. 目前论文最多能 claim 到什么？
8. 这一轮对 Position / Force / Integration 主线意味着什么？

不要堆大量代码、变量名和实现细节。

必须出现的专业概念，顺手用一句人话解释。
